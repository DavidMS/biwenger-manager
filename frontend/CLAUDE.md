# Frontend conventions

React 19, TypeScript (strict), Vite, Tailwind 4, shadcn/ui (Radix), TanStack Query 5, React Router 8. These rules add to the root `CLAUDE.md`. The `frontend-feature` skill gives the order of work for a new page or feature, and this file wins when the two disagree.

Use Node 24 (`nvm use` here). Before a PR, run what CI runs: `npm run lint && npm run format:check && npm test && npm run build`.

## Folder structure

```
src/
  main.tsx               entry: QueryClientProvider + RouterProvider, nothing else
  index.css              Tailwind and the shadcn theme (CSS variables)
  app/                   wiring: routes.tsx, navigation.ts, queryClient.ts
  pages/                 one component per route, e.g. MarketPage.tsx
  features/<feature>/    everything for one feature, e.g. features/market/
    api.ts               functions that call the backend
    types.ts             types for the backend's JSON
    hooks.ts             TanStack Query hooks and query keys
    <Component>.tsx      the feature's components, each with <Component>.test.tsx next to it
  components/
    layout/              app shell and page parts: AppLayout, PageHeader, SectionCard (a card that is a labelled region)
    state/               LoadingState, ErrorState, EmptyState: every data view uses them
    ui/                  shadcn/ui components, generated by its CLI
  hooks/                 hooks generated by the shadcn CLI (`components.json` points here)
  lib/                   shared helpers with no feature knowledge: utils.ts (cn), and later the fetch wrapper and formatting
  test/                  test setup and shared test helpers
```

- **Pages are thin.** A page puts a `PageHeader` and the feature's components together. Data fetching and logic live in `features/`.
- **A feature doesn't import another feature's internals.** If two features need the same thing, move it to `components/` or `lib/`. The one exception is the query-key object in `hooks.ts` (`marketKeys`): it is the feature's public API, so another feature's mutation can invalidate its queries.
- **Add a route in two places:** the route in `app/routes.tsx` and, if it belongs in the menu, the item in `app/navigation.ts`. The layout test fails if a navigation link has no page.
- Import with the `@/` alias (`@/components/layout/PageHeader`), not with `../../`.
- Create a folder or file when it gets its first content, not before.

## Components

- Function components with **named exports** (`export function MarketTable()`), one exported component per file, file named after the component in PascalCase. Small private subcomponents used only in that file (like `LastRun` in `SyncCard.tsx`) may stay in it.
- Props are a `type` named `<Component>Props`, declared above the component.
- Keep components small. When one fetches data and also renders a lot, split it: a container that calls the hook, and presentational components that take props.
- Every component that shows server data handles **loading, error and empty** states with `components/state/` (`LoadingState`, `ErrorState`, `EmptyState`), so every page looks the same. `ErrorState` shows the backend's problem title and detail; pass a `title` or `hint` when the view knows better.
- A page section is a `SectionCard`: a labelled region with a level-2 heading. Screen readers can jump to it, and tests find it with `getByRole('region', { name })`.
- Accessible by default: real `<button>` and `<a>` elements, a label on every input, `aria-label` on icon-only buttons, dialogs that work with the keyboard (shadcn's Radix components do this).
- All UI text is in English.

## Data fetching and state

- Server data goes through **TanStack Query**, never `useEffect` + `fetch`. Components never call `fetch` directly.
- `features/<feature>/api.ts` holds plain async functions that call `/api/...` through `lib/api.ts` (`getJson`, `postJson`) and return typed data. A non-2xx answer throws an `ApiError` with the backend's `status`, `title` and `detail` (the backend answers with problem details). `postJson` always sends `Content-Type: application/json`, which Phase 6 write endpoints require.
- When a sync finishes, the settings feature already refreshes every other query: a new feature's data is refreshed without doing anything.
- `hooks.ts` wraps them in `use<Thing>()` hooks and keeps the query keys in one object per feature:

  ```ts
  export const marketKeys = {
    all: ['market'] as const,
    list: (filters: MarketFilters) =>
      [...marketKeys.all, 'list', filters] as const,
  }
  ```

- Mutations invalidate the queries they change, including other features' (`queryClient.invalidateQueries({ queryKey: squadKeys.all })`).
- Defaults are in `app/queryClient.ts` (1 minute fresh, one retry, no refetch on focus). Change them per query only with a reason.
- UI state stays local (`useState`). Filters and sorting that should survive a reload go in the URL, through `useSearchParams`. No global store until something needs one.
- Routing is React Router 8: import from `react-router`, never `react-router-dom`. Use its data router for routes only, with no `loader` or `action` functions, so TanStack Query stays the one data layer.
- Recommendations come from the backend. The frontend shows them and their explanations, and never computes them.
- Any action that writes to Biwenger (bid, sell, accept offer, save lineup) opens a confirmation dialog that shows the consequences. It calls the backend's _propose_ endpoint, then _confirm_ only after the user agrees (root golden rule 2).

## TypeScript

- `strict` is on, plus `noUnusedLocals` and `noUnusedParameters`. No `any`. When a type is unknown, use `unknown` and narrow it.
- `import type` for type-only imports (`verbatimModuleSyntax` requires it).
- Types for backend JSON match the backend's response DTOs exactly. Money is a `number` of euros, as the backend sends it, and is formatted by one shared helper in `lib/`.
- Use `as const` for fixed lists, like `navItems`.

## Styling

- Tailwind utility classes in `className`. No CSS files besides `index.css`, no inline `style` except for values computed at runtime.
- Use the theme's tokens (`bg-background`, `text-muted-foreground`, `border-border`, `font-heading`), not raw colours like `text-gray-500` or hex values, so the theme stays in one place.
- Build with shadcn/ui first. Add a component with `npx shadcn add <name>`, which uses the CLI version in `package.json`, which writes it to `components/ui/`. Those files are generated: change them only when needed, and say so in the PR.
- Conditional classes go through `cn()` from `@/lib/utils` (generated `ui/` files import the `cn` package directly, which is the same function). Variants of shadcn components go through their `variant` and `size` props, or `buttonVariants()` for elements like `NavLink`.
- Prettier sorts the Tailwind classes. Don't sort them by hand.
- Layouts work from phone width up: use `flex-wrap` and the responsive prefixes (`md:`), and avoid fixed widths.

## Tests

- Vitest + React Testing Library + `user-event`, in jsdom. Test files sit next to the code: `MarketTable.test.tsx`.
- Query the way a user finds things: `getByRole('button', { name: 'Suggest buys' })`, `getByRole('heading', { level: 1, name: 'Market' })`. Not by class name or test id.
- Interact with `const user = userEvent.setup()` and `await user.click(...)`, not `fireEvent`.
- Mock the feature's `api.ts` module (`vi.mock('@/features/market/api')`), not `fetch`.
- Render with `src/test/render.tsx`: `renderWithProviders(<Component />)` gives a fresh `QueryClient` (no retries, no shared cache) and returns it; `renderApp(path)` renders the whole app. For polling, use `vi.useFakeTimers({ shouldAdvanceTime: true })` and `advanceTimersByTimeAsync`, never a real wait.
- `fetch` fails in every test (`src/test/setup.ts`) unless the feature's `api.ts` is mocked: a forgotten mock fails instead of calling a server.
- Cover the loading, error, empty and populated states of data views.
- Pure helpers (formatting money, sorting) get plain unit tests.
- Make a new test fail once (for example by changing a label) to see that it can.
- A small presentational component may be tested through its parent (as `PageHeader` is through the layout test). Components with logic or states get their own test file.
